🗺️ 项目总览 — 四大仓库协作机制

本文档是所有技术成员加入 RomanceSpace 的第一站。读完这篇，你将从宏观上理解系统的分工逻辑和信息流向，然后再深入到各自的仓库细节。

一、为什么要拆成四个仓库？

早期项目所有代码放在一个单仓库（monorepo）里，随着功能越来越多，维护成本急剧上升：改一行模板的样式，却要整体重新部署后端逻辑；设计师没有办法独立工作，必须让后端帮他们上传文件。

拆分的核心原则是：每个仓库只做一件事，任何人的改动都不影响其他模块的稳定运行。

⚙️ 后端 / 基础设施

RomanceSpace-Worker

整个系统的"神经中枢"。负责处理所有 HTTP 请求、路由分发、模板渲染和 API 鉴权。

🎨 前端 / 模板美工

RomanceSpace-Templates

存放所有可视化模板的资产（HTML/CSS/JS/图片）。开发者和设计师的主要工作区。

📄 文档 / 技术写作

RomanceSpace-Docs

本文档站点本身。记录系统架构、API 接口和运营指南。

🏗️ 产品 / 主站开发

RomanceSpace-Platform

用于开发面向终端用户的主站（CMS 管理后台、注册/购买流程等）。（开发中）

二、四大仓库如何互相协作？

系统运转遵循以下协作流程，理解这条数据链路是参与贡献的前提：

协作链路 A：模板上架流程

1
模板开发者（Templates 仓库）：在 src/my_card/ 下编写 HTML/CSS/JS，本地测试确认无误后，git push 到 GitHub。
↓
2
GitHub Actions（自动触发）：检测到 src/ 下有改动，运行 upload-template.js 脚本，携带 RS_ADMIN_KEY 密钥调用 Worker API。
↓
3
Worker（/admin/upload-template）：接收文件，存入 R2 存储，在 KV 数据库中更新版本号与字段信息。若该模板已有用户使用，触发后台批量重渲染。

协作链路 B：用户开通专属页面流程

1
主平台后端（Platform 仓库）：用户在主站选好模板、填写姓名等信息后，主站后端从 ADMIN_KEY 环境变量中取出密钥，向 Worker 发起 Server-to-Server 请求。
↓
2
Worker（/admin/render-page）：从 R2 读取模板 HTML，将用户数据注入占位符，生成静态 HTML，保存至 R2 + 更新 KV 路由表。
↓
3
用户访问：用户打开 xiaoming.885201314.xyz，Worker 命中 Cloudflare Cache（最快），再次命中则直接从 R2 读取预渲染 HTML，全程无需数据库实时查询。

四、快速上手：我该从哪个仓库开始？

我的角色 推荐第一步
🎨 前端 / 设计师 直接克隆 RomanceSpace-Templates，阅读《模板编写与上传教程》开始编写你的第一套模板。
⚙️ 后端 / DevOps 克隆 RomanceSpace-Worker，阅读《API 接口文档》，了解 Worker 的每个接口的参数格式与响应示例。
🏗️ 主站全栈 克隆 RomanceSpace-Platform，阅读《开通与修改用户网页》调通 /admin/render-page API 流程。
📄 文档 / 运营 克隆 RomanceSpace-Docs，直接修改 public/pages/ 下的 HTML 文件，推送后自动上线。
✅ 环境依赖： 本项目所有仓库只需要 Git + Node.js v18+ 即可参与开发，无需复杂的本地数据库搭建。后端逻辑完全运行在 Cloudflare Edge，本地只需开发和调试模板本身。
⚠️ 密钥管理：ADMIN_KEY / RS_ADMIN_KEY 等密钥永远不能出现在任何代码里或提交到 Git 仓库中。它们只能配置在 Cloudflare Secret 或 GitHub Repository Secrets 中。
