⚙️ Backend 服务端原理 (初学者笔记)

这份笔记将带你摸透 RomanceSpace-Backend 仓库。如果说前端是个“傻白甜”接收员，那后端（运行在独立 VPS 上的 Node.js/Express）就是这个系统里**拥有生杀大权的“铁血判官”和“重体力苦口”**。在 CQRS 架构中，它是绝对权威的“控制平面”与“写入引擎”。

💡 为什么这些不能放在 Cloudflare Worker 里算？ (分析)
1. 安全性：Cloudflare 代码人人都能随便访问，一旦不小心暴露了数据库密钥就完蛋了。VPS 是我们自己的锁上门的屋子。
2. 性能极限：把几千字的模板跟几千字的用户数据融合（正则替换），对 Worker 来说太费 CPU，很容易撞到 Cloudflare 的 10 毫秒运算墙。让 VPS 这个吃苦耐劳的老黄牛来算，算完扔给网关分发，这是最高效的做法。

一、 后端是怎么干活的？ (操作说明)

这个 Node.js 后端平时啥也不管，就等着你前端调 api.885201314.xyz 里的接口办事。它办两件大事：

  • 查案子与放行 (鉴权与过滤): 检查你存不存在，钱给了没，想注册的“子域名”是不是我们内部用的（黑名单系统！）。
  • 造网页与入库 (渲染融合): 作为系统唯一“造物主”，用自己的最高权限把最终网页造出来并入库。

二、 核心制版全流程 (怎样实现的)

当接收到调用请求 POST /api/project/render（生成网页）时，后台进行以下处理：

1
安全过滤与黑名单拦截
动作：VPS 后端立马去翻自己的“大脑内存”。看这个用户请求的域名（如 `admin` 或 `api`）是不是在 __sys__blocklist 字典里。
结果：如果是黑名单，直接扇回去报错。如果不是，进入下一步。（这段代码查内存只要 0 耗时，且不烧 KV 额度，因为我们在内存里把它长久缓存了）。
2
提取原厂骨架 (取模板)
动作：使用后台的 Cloudflare 特权密钥，以迅雷不及掩耳之势去 R2 仓库提一个干净的 index.html 模板出来。
3
急速熔铸与变身 (正则计算)
动作：这是 VPS 唯一出力流汗的地方。它用极高强度的正则匹配算法，把原始 HTML 里像 `{{lover_name}}` 这样的占位符，全都硬编码替换成前端传来的“小红”和“小明”。
4
送进仓库，挂上路由榜
动作：生成的这段新 HTML 直接写死塞进 R2 (放进 `pages/xiaoming/index.html` 里！)。然后通过 SDK 告诉 Cloudflare KV：“这有个叫 xiaoming 的，你可以放行了”。最后把这笔交易记录记在咱们最安全的 Supabase 数据库上。

三、 核心特权与底层配置

⚠️ 机密重地配置 (.env)：
这里掌握着整个体系的命脉：
SUPABASE_SERVICE_ROLE_KEY (无视权限查数据的尚方宝剑)
R2_ACCESS_KEY_ID (进出云仓库的万能钥匙)
这就是为什么前面说，所有重体力写入与查询，都只能在这里收口。

看看底层我们是怎么暴躁推包的（utils/cf.js 样例）：

// 抛送静态页面给 R2 仓库的动作
export const putToR2 = async (key, buffer) => {
    // 采用 AWS S3 标准流连法，打通咱们的 Cloudflare R2
    const client = new S3Client({
        region: 'auto',
        endpoint: process.env.R2_ENDPOINT,
        credentials: { 
            accessKeyId: process.env.R2_ACCESS_KEY_ID, 
            secretAccessKey: process.env.R2_SECRET_ACCESS_KEY 
        }
    });
    // 以 Buffer 将 HTML 直接抛进去！
    await client.send(new PutObjectCommand({ Bucket, Key: key, Body: buffer }));
}
