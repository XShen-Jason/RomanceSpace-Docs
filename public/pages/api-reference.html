🗄️ 后端核心 API 开发规范 (Backend API Spec)

做为即将在 RomanceSpace-Backend 仓库中大展身手的后端开发者，你需要实现并暴露以下核心接口。所有的前端 UI 表单最终都会汇总为对下述 万能熔铸接口 的书面诉求。

💡 接口职责提醒： 你的 /api/project/render 接口不仅要返回成功信号，内部还需要顺序或并发执行：
1. 读取 R2 获取模板骨架。
2. 正则拼装生成最终 HTML 并写回 R2。
3. 写入 Cloudflare KV 标记路由存活状态 (status: 1)。
4. 写入 Supabase 永久存档用户的配置流水。

核心接口：生成与更新项目全能王 ⚙️

POST https://api.885201314.xyz/api/project/render

1. 请求参数 (Request Body - application/json)

参数名 类型 必填？ 说明
subdomain String 必须 申请的专属三级域名前缀。必须是全小写字母或数字的组合，如 xiaoming。后端需负责校验查重。
type String 必须 使用的模板代号（如 love_letter）。后端需去 R2 拉取该模板对应的源文件 [type]/index.html。
data Object 必须 注入该模板的详细业务数据（JSON 对象，不可随意捏造，需严格吻合模板的 schema 设定）。
🎨 前端发起 Fetch 示例 (请求桩)
// 无论用户是首次开通还是二次修改，统统 POST 这个万能 Payload
const payload = {
  "subdomain": "xiaoming",
  "type": "classic_love",
  "data": { 
    "names": ["小明", "红红"], 
    "startDate": "2023-01-01",
    "background_music": "https://..."
  }
};

const response = await fetch("https://api.885201314.xyz/api/project/render", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload)
});

2. 后端服务端预期处理流程 (内部流转)

1
参数防灾校验：使用 Zod 或 Joi 查验传入的格式；查验 KV 该前缀是否属于当前用户/尚未被抢注。
2
并行外联动作：
- R2 操作： 调用 S3 Client，将合成后的纯净 HTML (`generatedHtml`) `PutObject` 进存储桶，键名为 xiaoming.html。
- KV 操作： 写入 {"xiaoming": {"status": 1, "template": "classic_love"}}。
- Supabase 操作： 将整个 payload 序列化为 JSON 塞入关系库长期留档。

3. 多场景请求与响应范例集 (Use Cases & Responses)

为了保证前后端对接的严谨性，以下列出了 3 种最核心的交互场景及其标准的 JSON 响应对照：

✅ 场景 A-1：零号起步 (首次领用免费域名并绑定模板)

业务说明：新用户注册后，首次抢占了 xiaoming 这个前缀，并选择了一个基础模板 classic_love，填入了初次见面的数据。

前端 Payload
{
  "subdomain": "xiaoming", // 后端查 KV 发现该名字为空，允许通过，并绑定给该用户ID！
  "type": "classic_love",  
  "data": { "names": ["小明", "红红"], "startDate": "2023" }
}

✅ 场景 A-2：喜新厌旧 (不换域名，仅更换整个模板)

业务说明：小明觉得原模板不好看，保留 xiaoming 的域名，但要求更换为高级的 3d_gallery 模板。此操作需耗费大量 VPS 性能拉去新模板。

前端 Payload
{
  "subdomain": "xiaoming", // 后端查全表证实身份：该前缀确实一直属于小明自己，放行！
  "type": "3d_gallery",    // 【产生变更】Backend 将去 R2 重新拉取 3d_gallery 的骨架
  "data": { "images": ["url1", "url2"] }
}

✅ 场景 A-3：小修小补 (不换域名不换模板，仅修改内容字句)

业务说明：小明和红红放假去玩了，只想替换其中一张照片或更新一下恋爱天数，模板依旧是 3d_gallery。

前端 Payload
{
  "subdomain": "xiaoming", // 身份验证通过
  "type": "3d_gallery",    // 模板没变
  "data": { "images": ["url1", "url_new_trip"] } // 【产生变更】仅仅是 data 载荷里的某个字段改变了
}

❌ 场景 B：域名前缀被他人抢注 (HTTP 400)

前置条件：表单里的 xiaoming 已经在 KV 中被别人占用了。后端在执行第一步查重时就拦截退回。

前端 Payload
后端 Response
{
  "subdomain": "xiaoming", // 该前缀已存在且属于另一个用户ID
  "type": "classic_love",
  "data": {}
}
{
  "code": 4010,
  "message": "该域名前缀已被他人抢先使用，请更换试试哦",
  "data": null
}

⚠️ 场景 C：参数格式遗漏或违规 (HTTP 400)

前置条件：前端漏传了必填的 type，或者 subdomain 包含了中文等不合法字符。后端 Zod/Joi 校验失败。

前端 Payload
后端 Response
{
  "subdomain": "小明", // 中文不符合域名规范
  "data": {} // 漏传了 type 字段
}
{
  "code": 4001,
  "message": "参数校验失败: 'subdomain' 只能包含小写字母和数字, 'type' 为必填项",
  "data": null
}

💎 商业化与配额架构建议 (VIP Monetization & Limits)

结合您所使用的 Cloudflare 免费额度 (Free Tier) 以及 Node.js VPS 的单机计算性能，我们在设计后端的扣费/计次拦截逻辑时，强烈建议采用以下策略：

1. 域名配额管控 (控制 KV 记录泛滥)

  • 免费限制：系统强制默认，一个注册账号仅限绑定 1 个自定义免费前缀（如 xiaoming）。
  • 多余域名增购：如果用户还想给别的女生建网页，必须付费解锁第 2、第 3 个额度。
  • 技术依据：CF 的 KV 虽然免费读取无限，但免费的 Write 请求只有 10万次/月。死死限制单个账户的新增域名数量，可以彻底杜绝恶意刷爆你的 KV 额度，保证 10万次全用于真实的优质付费用户上。

2. 更换模板/修改数据的频次管控 (保护 VPS 性能)

  • 免费限制：普通用户“修改内容”或“更换模板”（即调用上方 API 的操作），可以限制为 每月/每天 3 次或 5 次 免费生成机会。
  • VIP 会员特权：开通 VIP 月卡，可以享受 每月 100 次 或无限次的重新生成修改特权。
  • 技术依据：由于每次切换模板，您的 VPS 都要跑去 R2 拉取空壳并执行一次 CPU RegEx 正则替换运算，如果几万人同时高频点击“切换模板”，普通的 2 核 4G VPS 会瞬间 CPU 100% 宕机。同时，R2 的 PutObject 操作每月免费只有 100万次，计次收费能够有效防 DDOS 和恶意并发消耗。

3. 废弃域名的回收机制 (避免幽灵占坑)

  • 为了防止前缀被无限占用，后端数据库 Supabase 中应该有 last_login_at 或 expired_at 的设计。
  • 对于免费账户长达半年不登录的“僵尸前缀”，写一个定时任务跑批处理，去 KV 中将它的 status 设为 0，并释放名字给他人购买，实现资产盘活。
