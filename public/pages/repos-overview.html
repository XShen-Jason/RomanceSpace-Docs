🗺️ 项目总览 — 四大核心仓库协作机制

本文档是所有技术成员加入 RomanceSpace 的第一站。读完这篇，你将从宏观上理解 CQRS 拆分后的系统分工逻辑和信息流向。

一、为什么采用 CQRS 和微仓库拆分？

早期 RomanceSpace 尝试过 All-in-One 单仓库，导致部署非常沉重：UI 的一点小修订会阻断核心计算逻辑。我们最终采用**指令与查询职责分离 (CQRS)**思想，切分为四个拥有极高内聚的微型代码库：

拆分原则： 任何人的修改与发布都不影响其他模块的可用性。

⚙️ 后端 (写入引擎)

RomanceSpace-Backend

基于 Node.js，负责接管所有复杂的逻辑组装、模板解析、Supabase 写入和 R2 HTML 打包。它是系统的**重度计算核心**。

🎨 前端 (UI 交互)

RomanceSpace-Frontend

基于 Vite / React 构建的 SPA 应用。负责全部 C端用户界面展示、填写表单，与 Backend 直接用 API 对话。

🌐 边缘网关 (读取引擎)

RomanceSpace-Worker

基于 Cloudflare Worker。极其轻薄，无任何业务逻辑。专门负责从 CDN / R2 取货发给全球访客，实现**抗揍极速分发**。

📄 文档资料

RomanceSpace-Docs

本文档站点源码库。由 GitHub 无脑推送到 Pages。

二、核心流水线：四大仓库如何互相协作？

以下展现了一个完整的“用户定制专属网页”背后的信息传输接力赛：

1
UI 交互 (Frontend仓库)：小明在前端界面选了一个恋爱模板，输入二人名字，点击提交。前端立刻向 API api.885201314.xyz 发送 JSON 格式请求。
↓
2
强写逻辑 (Backend仓库)：收到数据，从深处挖出这套模板原始文件。将其与小明的文字“熔铸”成无法再更改的死块 HTML。随后持久化入超大型数据库。
↓
3
分发登记 (Backend仓库)：Backend 把熔铸好的 HTML 重力扔进了 Cloudflare 的 R2 仓库。同时在 KV 记事本 悄悄记下：xiaoming -> 有效期。
↓
4
极速展现 (Worker仓库)：第二天无数人访问 xiaoming.，流量打到了守在前门的门口保安（Worker）。保安一查 KV 说有效，马上从 R2 拉了 HTML 复印无数份塞进缓存里，全部发走。
