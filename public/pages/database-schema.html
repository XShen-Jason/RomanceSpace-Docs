📊 数据库极简表结构设计 (Supabase)

真理源点： 在这个拥有诸多组件的云端系统中，Supabase PostgreSQL 是业务真理源（Source of Truth）。一旦发生系统崩溃或其他云组件数据丢失，VPS 后端可以完全依托 Supabase 中的这些记录，将所有的静态页面重新编译成形并全网下发。

主要数据表关联说明

目前只有 2 张核心宽表。由于我们并不自研繁冗庞大的 CMS 管理系统，而是快速迭代 C端需求，字段采用弱外键耦合 + JSONB。

一、 templates 表（模板库登记）

该表用于登记开发者上传的所有可用模板的配置信息。该数据表只被 VPS 读取。如果模板需要修改 `schema.json` 里的 fields，这里存放的是最新版。

字段名 类型 默认 / 约束 说明
id uuid PK, gen_random_uuid() 主键
name varchar UNIQUE, NOT NULL 代号，如 love_letter
version integer DEFAULT 1 随着持续更迭的模板包计数
schema jsonb NOT NULL 存放原生 schema.json 文件的完整抽象结构与 default 默认占位映射
created_at timestampz now() 模板诞生时间

二、 projects 表（用户生成实例）

保存最终每一位用户填入模板的关键数据。有了这张表，用户更改数据，或者系统整体想发大版本强制重新渲染一遍全网页面，就有了弹药储备。它是平台的核心变现资产。

字段名 类型 默认 / 约束 说明
id uuid PK, gen_random_uuid() 主键
user_id uuid NULLABLE 所有者 (关联 auth.users 外键)，留空代表游客生成
subdomain varchar UNIQUE, NOT NULL 路由网关依据，例如 xiaoming。绝不会撞车。
template_name varchar FK -> templates(name) 用户当时选择挂载的模板。如要给用户换壳，改这里。
raw_data jsonb NOT NULL 用户当场在页端填写的 JSON 内容。如：{ "title": "纪念日", "startDate": "..." }
status varchar DEFAULT 'active' 用于下架禁用恶俗网址。封禁改为 `banned`
updated_at timestampz now() 用户上回变动内容的时间。

为什么把 raw_data 写成了 JSONB？而不是把 title, startDate 之类的各自建字段？

每一个模板对数据的诉求五花八门，有的模板有 2 个参数，有的则有 50 个数组与字典组合参。将表单定制结果浓缩在这一个扁平轻快的 jsonb 黑盒中，能使整个后台引擎永不报错，极度适应未来一百万套各种异形模板的上架。
