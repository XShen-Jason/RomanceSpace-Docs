🗄️ 核心创建接口 (API Reference 笔记)

这个接口是整个系统的“造物主”按钮。无论用户在前端怎么折腾，最终都是把数据打包，调这个接口来一锤定音（生成静态网页）。

💡 接口唯一性规则 (说明)：
我们没有把 `首次创建` 和 `后续修改` 分开成两个接口。不管用户是第一次买，还是买完后想改个字，统统 POST 调这一个 /render 接口就行。这种“幂等性”设计极大地减少了代码量，符合极简主义。

一、 接口详情 (怎样调用的)

POST https://api.885201314.xyz/api/project/render

1. 请求 Payload 参数

字段 说明 必填
subdomain 申请的域名前缀 (例如 xiaoming)。后端会拿去和 KV 黑名单对撞查重。 必须
type 模板的文件夹名字 (例如 classic_love)。这决定了后端去 R2 抄哪套房子的底。 必须
data 你想往模板里塞的字和图片。必须是一个 JSON 对象，长啥样由模板的 schema.json 说了算。 必须 
// 前端发送的真实样板
const payload = {
  "subdomain": "xiaoming",
  "type": "classic_love",
  "data": { 
    "names": ["小明", "红红"], 
    "startDate": "2023-01-01"
  }
};

const res = await fetch("https://api.885201314.xyz/api/project/render", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(payload)
});

二、 背后运作流程与场景 (流程与分析)

在这个单口 API 的背后，后端进行了极其复杂的运算（但这一切对前端都是透明且优化的）：

1
场景 A: 全新开通 (首次发包)
当查到 xiaoming 没人用时，后端会直接将它绑定给当前用户，去拉模板、渲染HTML、写入 R2 并在数据库中建立小明的个人档案。
2
场景 B: 小修小补 (同域名二次提交)
如果小明觉得刚才打错字了，又点了一次提交。后端核查 xiaoming 依然是这哥们的资产，于是直接强制覆盖 R2 里的旧 HTML。这种覆写不会占用任何多余的存储空间。
3
场景 C: 惨遭拦截 (撞车与违规词)
如果“张三”填了 xiaoming 提交，或者有人填了保留字 api。由于后端第一步就比对内存里的零配置黑名单（Zero-Quota Blocklist），或者查到已经被小明持有了，会立马报错返回 400 状态码，坚决不会走到耗费算力的“拉模板和写 R2”那一步。
⚠️ 商业收费防护阀 (防破产提醒)
虽然 R2 和 KV 有免费额度，但这个接口因为要消耗 VPS CPU 执行正则渲染，且每次都会消耗 R2 宝贵的写额度 (Class A)。
未来当你开启收费时，在这个接口的头部，必须加入 Rate Limit (频率限制) 和额度扣除逻辑。比如每天免费用户只能提交 3 次，防止被竞争对手用脚本恶意轰炸你的 `api/render` 接口导致 VPS 宕机。
