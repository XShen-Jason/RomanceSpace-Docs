Chapter 3

数据脉动：端到端的全周期流转

在上帝视角下，数据并非静止。让我们通过“小明”创建一个浪漫网页的具体场景，来拆解数据是如何在各个服务间穿梭的。

1. 场景：小明建站的全套流程

阶段 A：前端造壳 (Collection Phase)

他在 www.885201314.xyz/builder 选好模板，填入情话。此时数据存在于小明的浏览器内存中。

💡 例子 (Payload)：
POST /api/project/render
数据包：{ subdomain: "wedding", title: "致小红", content: "永远爱你" }

阶段 B：后端重铸 (Double-Track Write)

VPS 收到请求后执行“双轨写入”以确保数据的一致性与分发的极速性：

1
Supabase (业务真理)：持久化存储项目配置（subdomain, template_id, raw_data）。这是判断权限的依据。
2
R2 (分发真理)：生成成品 HTML 强行覆盖 pages/{subdomain}/index.html。
3
KV (路由查重)：KV 写入脱水优化。只有当首次创建或模板切换（导致路由逻辑变动）时才写 KV。普通的文字内容修改不会触发 KV 写入，从而保护 1000次/天的有限配额。
4
CDN Purge：调用 Cloudflare API 实时秒级清除旧缓存。

阶段 C：全球分发 (Delivery Phase)

当小红点开 wedding.885201314.xyz 时：

  1. Worker 拦截请求，发现主机名中包含 wedding。
  2. 查询 KV，确认这个域名在库中且是激活状态。
  3. 调取 R2，直接流式读取 pages/wedding/index.html 内容。
  4. 返回用户，并贴上 Cache-Control 让 CDN 节点记住它。

2. 数据的“写时强覆盖”哲学

为了极致简化逻辑并节省费用，我们采取了 **“0 垃圾覆盖法则”**：

  • 不产生新文件名：用户修改内容时，后端永远是针对同一个路径 pages/{id}/index.html 进行强制覆盖。
  • 缓存刷新：覆盖写入后，后端会通过 Cloudflare OpenAPI 对该 URL 执行 Purge 操作，秒级清除旧缓存。
⚠️ 重要提醒：
KV 的每天免费写入额度仅 1000 次。这是我们唯一的短板。我们严禁在 KV 中存储长篇用户文字，KV 只存路由状态！真正的长文本永远存储在无上限的 R2 静态文件中。
