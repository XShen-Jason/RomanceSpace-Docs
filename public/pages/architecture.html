🚀 核心概念与工作原理 (基于 CQRS 读写分离)

这是一个极度优化的高并发小网页分发平台（RomanceSpace）。为了能在近乎“免费”的前提下支撑极高的访问量，系统底层经过了 CQRS（命令查询职责分离）深度设计。

阅读本文，你将了解这套被称作 “VPS 写时预渲染 + Worker 边缘 Cache 极速分发” 的架构到底是怎么运作的。

一、 五大核心组件通俗比喻

整个系统由一台重型计算服务器和四个 Cloudflare 边缘组件相互协作完成：

1. VPS 后端 核心中央流水线

通俗比喻： 公司的核心工厂。所有的脏活累活都在这干。

它的作用： 接收创建请求，将半成品模板和用户数据拼接成最终的静态 HTML。同时将数据永久存入数据库，并将 HTML 包裹送往 Cloudflare R2 仓库。

2. CF Worker 全球分发门卫

通俗比喻： 遍布全球的无情前台接待员（绝不做计算组装活儿）。

它的作用： 拦截用户的网址访问，判断网址有效性。只负责“去仓库拿写好的 HTML 网页给访客看”，实现全球秒开。

3. KV 登记处指示牌

通俗比喻： 一本极其轻薄的小本子。里面只写谁用什么模板（例：xiaoming -> /pages/xiaoming.html）。

它的作用： Worker 接客时，秒查小本子，看这个人开通网页没。如果没开通直接赶走（极速返回 404）。

4. R2 无限大仓库

通俗比喻： 一个不用付快递费（出口流量免费）的超大静态仓库。

它的作用： 存放海量静态文件（图片、CSS样式、音乐）以及由 VPS 后端推送过来的所有**最终静态 HTML 页面**。

5. Cache 门口的免费橱窗

通俗比喻： 前台门外的展示大屏。路口的人直接看大屏，连门卫 (Worker) 都不用打扰。

它的作用： 免费帮我们阻挡 99% 的请求压力。网页被访问一次后，就会在这个橱窗缓存。之后一万个人来看，连 Worker 的请求调用数都不耗费！

二、 核心工作流程（图解）

我们将整个系统拆解为三个步骤，完美展现 CQRS 的 写算力集中化 和 读算力边缘化：

流程 ①：开发者上传一套“半成品模板”

【管理员/开发者 调用 Backend API】上传 ZIP 模板包
        │
        ▼
[VPS 后端 接收并解析]
        ├── 将 index.html, style.css 传进【R2 仓库】对应的版本号目录下。
        ├── 将模板参数写入 Supabase 并配置同步到【KV 指示牌】上。
        └── 将默认预览页面直接渲染出来。

流程 ②：主平台为“小明”开通专属页面 (强写链路)

小明在前端界面填好数据后：

【前端】 -> POST `api.885201314.xyz/api/project/render` 带上 "我爱你"
        │
        ▼
[VPS 后端 开始重度组装 (预渲染)]
        ├── 从【R2 仓库】拉取模板源代码和参数结构。
        ├── 进行复杂的字符串插值，把 "我爱你" 塞进 HTML 里的 {{ta的名字}} 中。
        ├── 存库：将用户的原始 JSON 表单存入 Supabase 持久化。
        ├── 关键一步：把这份做好的 HTML（小明专属版），推送覆盖到【R2 仓库】。
        ├── 在【KV 指示牌】写下："xiaoming 路由有效"。
        └── 通知 Cloudflare API，让旧的【Cache 橱窗】缓存失效。
核心优势：为什么让 VPS 渲染？
如果在 Worker (边缘节点) 里做字符串插值和验证，受限于免费节点的 CPU 限制，极其容易遇到死锁或超时。让 VPS 在主干线路一次性把 HTML 死硬块“预组装”出来，Worker 只需要当一个没脑子的送货员，性能能够暴涨一万倍。

流程 ③：小明的朋友们猛烈访问页面 (极速读链路)

几万个人同时打开网址 `xiaoming.885201314.xyz`
        │
        ▼
请求来到全球 Cloudflare 边缘节点
        │
        ├─ 查【Cache 橱窗】找到小明的网页了？ 
        │    ✅ 直接返回！(0延迟，无需任何计算)
        │
        └─ 如果橱窗里刚好没找到 (如第一次访问)
             │
             [Worker 路由] 被唤醒，光速看一眼【KV 指示牌】确认有小明。
             转身进去【R2 仓库】，把 "小明的固定 HTML死硬块" 提出来。
             交给访客，顺手在【Cache 橱窗】贴一张缓存，之后一小时内的人全去看缓存。

三、 总结

CQRS 把读和写完全拆解：

  • 写（Write）由于并发量低、计算复杂，交由独立自主的 Node.js VPS 后端稳扎稳打。
  • 读（Read）由于并发量极高、计算几乎没有，交由 Cloudflare Worker 从 R2 提取缓存给全世界。

这极大规避了 Serverless 的各种 CPU 使用率上限，也是这套系统之所以快如闪电的最终秘密。
